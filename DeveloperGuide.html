Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

UI component

The UI displays member, equipment and loan records and accepts commands from the operator. MainWindow connects the command box, feedback, navigation and read-only record panels. Commands reach Logic through one execution callback; panels do not mutate domain records directly.

The API is specified in Ui.java.

CommandResult contains a typed DisplayRequest telling the shell which view to show. A directory request with a query applies those criteria; one without a query preserves the current criteria. Member selection uses NUS ID and equipment selection uses UUID, so a refresh can recover the selected record after an edit. Model notifications are combined into one queued refresh. Programmatic selection and refresh do not submit another command.

Equipment groups are derived from category and name. Each group retains its distinct physical units; selecting a group does not select an arbitrary unit. Member and equipment details link to related records through identity-based commands. LoanPanel shows open and completed loans and shares its identity filters with command-based navigation.

CommandPreview copies text or prepares the command box for review; execution requires Enter. Open-loan rows can prepare a return with an optional observed condition. ResultDisplay presents a compact summary with Details and Copy actions for long feedback. Help and Tab completion reuse the command vocabulary. The inherited person panel is outside supported navigation.

LaplaceTheme.css and LaplaceFonts centralize appearance. mode dark and mode light update GUI preferences without changing records or undo history; appearance and window geometry are saved on shutdown. Layout tests cover the supported screen sizes, while font tests check the resolved faces. See Testing for the shared JavaFX runtime and execution instructions.

Below 600 logical pixels of scene height, compact spacing and wider minimum directory panes preserve record visibility. Collapsed feedback places its heading beside the text; Details and Copy retain the complete result. verifyPackagedLayout repeats the layout tests with production classes/resources loaded from the built JAR and checks that code source explicitly. Logical-size tests do not establish actual operating-system scaling support.

Command routing and legacy compatibility

LogicManager.execute() first calls AddressBookParser.parseCommand(). The root parser accepts member, equipment, and loans, delegating to their family parsers and then the appropriate leaf parser (for example, EquipmentCommandParser and EquipmentAddCommandParser). It also accepts undo, redo, mode, help and exit. Family and leaf parsers remain responsible for validating subcommands and arguments.

The retired top-level words add, edit, delete, clear, find, and list now reach the existing unknown-command branch and throw ParseException("Unknown command."). In particular, list members is rejected; the supported command is member list. Rejection occurs before a command is constructed or executed, before a transaction candidate is created, and before storage is called.

For supported commands, LogicManager executes transactional mutations on an isolated model candidate, saves that candidate state, and publishes it to the live root only after saving succeeds. Commands marked isReadOnly() return without saving. This retirement does not change those execution rules.

AddressBook is still the shared root for persons, members, equipment, and loans. Its name and the getAddressBook()/saveAddressBook() APIs do not identify disposable person-only behavior. Existing JSON persons data is retained and round-trips when supported commands save. Person value classes used by members, legacy command/parser implementations and their unit tests, and the legacy UI panel remain for a separate dependency-aware cleanup. Removing public routes does not remove stored records.

Model component

The Model owns the in-memory records and their consistency rules. A Member is identified by NUS ID, an Equipment unit by UUID, and a Loan connects those identities. AddressBook checks relationships across records; the individual collections enforce identity uniqueness. ModelManager exposes stable observable lists, derives availability and coordinates transaction candidates and undo/redo history. Views observe these lists without owning or editing their backing collections. Mutations run on an isolated copy, called a candidate. Publication updates live records only after that copy is saved.

Storage component

Storage loads records and preferences from local JSON and saves changes without exposing partial files. StorageManager delegates to one JSON storage class for each file. Adapters convert stored text into immutable domain values, and the root validates references before a loaded dataset is accepted. Record mutations save an isolated candidate before the live Model is updated. Invalid loads and failed saves preserve the existing data file.

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Directory search and inventory planning

MemberCommandParser and EquipmentCommandParser delegate search arguments to DirectorySearchCommandParser. It validates the allowed prefixes and sort fields, then constructs an immutable DirectoryQuery and a DirectorySearchCommand for the requested directory. Search defaults to active records; status/deleted and status/all expose retained records.

The sequence below shows successful execution of member search q/alice sort/name. Parsing, collection iteration, and result-object construction are omitted to focus on the read-only command path. data is the ReadOnlyAddressBook returned by the model.

DirectorySearchCommand counts matches using DirectoryQuery, then returns a CommandResult containing DisplayRequest.members(query) or DisplayRequest.equipment(query). Since the command is read-only, LogicManager returns without creating a transaction candidate or saving data. Equipment queries additionally use Model.getAvailability to derive availability from current state.

DirectoryQuery.members(data, eligible) combines caller eligibility with the member status filter. DirectoryQuery.equipment(data, lookup, eligible) applies eligibility and equipment status before resolving availability. Active totals exclude deleted records, while retained identities and loan history remain available for details and restoration. These query helpers do not change the stored schema.

MainWindow passes the same query to the directory list and its summary before refreshing them. Both evaluate the query against current data, keeping displayed rows and matching counts consistent. Sorting affects derived result lists rather than stored records. Navigation requests without a query preserve the current criteria; explicit list commands pass DirectoryQuery.all() to reset them. After mutations, the shell refreshes the views with their retained queries and recovers selection by NUS ID or equipment UUID when possible.

EquipmentDirectorySummary.refresh builds inventory summaries with InventoryGroups.group, passing DirectoryQuery.all().equipment(data, availabilityLookup) as the matching units. It formats each group using EquipmentPresentation.counts(group.units(), availabilityLookup). The activity below shows this GUI path when availability can be resolved; it does not describe the retained summarize helper.

Each group uses a pair of normalized category and name values, keeping the two keys separate even when either contains a display separator. InventoryGroups.group retains all physical units under each key and emits groups in first-match order. For this caller, the all-records query supplies default category/name/UUID order, so groups appear in category/name order. Other callers can pass a filtered or sorted matching list; group.matching() records those matches while group.units() retains the full group. The summary uses the all-records query, so its group counts are independent of search filters.

EquipmentPresentation.counts looks up each active unit's availability by UUID and counts deleted units separately without an availability lookup. It displays zero for absent availability states and adds a deleted count only when nonzero. The summary prefixes these counts with the category and name of the first unit in the group, preserving its stored spelling rather than displaying the normalized key. If its initial scan cannot resolve an active unit's availability, the summary displays Inventory groups unavailable: inconsistent equipment data. instead of group lines. These derived summaries preserve individual equipment identities and do not introduce a stored quantity field.

Adding multiple physical equipment units

EquipmentAddCommandParser accepts optional count/ through LaplaceArgumentParser, retaining its left-to-right validation and duplicate-prefix checks. Counts default to 1 and must be ASCII digits with a numeric value from 1 to EquipmentAddCommand.MAX_COUNT (100). The command constructor also validates the range for direct callers. The cap bounds accidental bulk creation and feedback size.

EquipmentAddCommand reserves all identities before inserting units. A local set prevents duplicate UUIDs within the batch; Model.hasEquipment excludes already-stored UUIDs. Each unit has a bounded 100-attempt generation budget. The command computes an advisory duplicate-description warning against the pre-batch records, then inserts units into the candidate model supplied by LogicManager.

The existing transactional path saves that candidate once and publishes only after success. Generation failure leaves the candidate untouched; insertion or persistence failure discards the candidate without changing live records. Equipment editing, deletion and restoration

Each Equipment is an immutable physical unit. EquipmentEditCommand builds a replacement with the stored UUID and any supplied details. AddressBook.setEquipment permits only active-to-active edits; UniqueEquipmentList.setEquipment checks UUID equality and replaces the value at the same index. Name/category changes affect derived inventory groups, never sibling units. Unspecified legacy text is retained verbatim; new text uses equipment-add validation. Notes can be cleared explicitly.

AddressBook.removeEquipment now marks a unit deleted after checking that no open loan exists. restoreEquipment clears the flag. Both retain UUID, details and closed loans. This supersedes the historical scaffold's permanent deletion. Member and equipment restoration have no time limit.

Lifecycle is separate from condition and loan status. Editing condition while loaned is allowed: ASSIGNED remains derived from the open loan; on return the edited condition controls availability. Deleted units derive UNAVAILABLE, cannot receive open loans, and are excluded from active availability counts. Inventory groups retain them and report their deleted count separately. Root loan validation applies this invariant both to new loans and complete dataset replacement/loading.

JsonAdaptedEquipment writes a boolean deleted. An absent flag defaults to false for earlier files; explicit null and non-boolean values fail loading. Closed loans may reference deleted equipment. All maintenance commands are transactional: execute against a candidate, save atomically, then publish. No-change/rejected edits and failed writes leave live state and previously saved bytes unchanged.

Directory queries share DirectoryQuery.Status across members and equipment. Equipment search defaults to active; status/deleted|all exposes retained units. List resets to all states without recording history. Cards label deleted units; details show lifecycle state and a restore command. Edit/restore navigate to the same UUID, retaining query criteria even if that unit no longer matches. Total counts include deleted units; availability counts include active units only, while groups also report retained deletions. The Loans tab and entity details show the retained completed loan history.

Undo/redo feature

The CLI commands undo and redo restore complete record states within the current session. AddressBookHistory is an immutable value owned by ModelManager, composed with the existing AddressBook rather than replacing or subclassing its observable root. It retains at most ten reversible changes (eleven history states). Each history state has independent collection containers for members, physical equipment, loans and retained legacy persons; immutable entity values may be shared.

The class diagram below shows only the command, persistence and record-history collaborators. Parser classes, collection wrappers, domain entities and preferences are omitted. The live model and each candidate own separate roots; multiple immutable history values may reference the same private stored history states. Accordingly, sharing these states uses ordinary associations rather than exclusive composition. The ordered states association has multiplicity 0..11, including empty history before the first change. An AddressBook history state has no ModelManager, and the package constructor can reuse a supplied root, hence 0..* at the model end of that association. Every model still refers to exactly one root. The logic associations allow model/storage collaborators to be shared by more than one LogicManager instance.

The first successful mutation records both the preceding state and the candidate state. Later mutations append a history state and a short action description, such as equipment add, without retaining command parameter values in the description. Once ten changes are retained, the oldest change and its preceding history state are discarded. A batch creation, issue or return is one history entry regardless of unit count.

Transaction and persistence boundary

  1. AddressBookParser routes bare undo/redo through their no-argument parsers. Both reject extra text and prefixes using LaplaceArgumentParser.
  2. LogicManager creates an isolated candidate through Model.createTransactionSnapshot(). Candidate records and preferences are copied; the immutable history can initially be shared safely.
  3. An ordinary transactional command changes candidate records. Command.recordsHistory() tells LogicManager to call recordAddressBook(previous, description) on that candidate. A real change discards any redo branch; an unchanged candidate leaves history untouched.
  4. UndoCommand/RedoCommand instead check availability and navigate the candidate's existing history. They return DisplayRequest.unchanged() and do not record another action. Redo restores the recorded history state directly, preserving UUIDs, loan dates, conditions and references without replaying commands.
  5. The existing atomic JSON save persists the candidate records once. Only after success does Model.publishTransaction() publish the candidate records and history to the live model. It preserves the live observable root and current preferences. Parse, validation and save failures leave live data, history position, redo availability and the previously saved file unchanged.

Record replacement validates all collections before publishing. AddressBook.resetData() installs the new records and runs the model's history-publication action before resuming list notifications. This keeps synchronous observers' record values and undo/redo availability consistent during transaction publication, explicit whole-model replacement, and direct undo/redo navigation. Validation failures leave the previous history intact; replacing identical records can still update history without list events.

The logic sequence traces one undo through parsing, availability checks, candidate execution, atomic saving and publication. AddressBookParser delegates argument validation and command construction to UndoCommandParser. The Storage lifeline abbreviates StorageManager, JSON serialization and AtomicFileWriter. Invalid arguments stop during parsing; unavailable undo stops during execution. Neither reaches saving. A save error discards the staged result without consuming a live history step.

The next two sequences expand only the model operation inside that candidate. They distinguish the candidate's stable root from the defensive copy returned by getCurrentState(). before and restored are separate immutable history values; position changes never mutate a history shared with the live model. Field assignment is shown as a note, rather than as a fictitious method call.

redo follows the same logic/save/publication sequence with RedoCommandParser, RedoCommand, canRedoAddressBook() and redoAddressBook(). Its unavailable error is Nothing to redo..

The model exposes canUndoAddressBook(), canRedoAddressBook(), undoAddressBook() and redoAddressBook(). Direct history navigation requires an available step; commands translate unavailable history into Nothing to undo. or Nothing to redo.. Successful feedback identifies the action: Undid: equipment add. or Redid: equipment add.. The history object guards invalid direct navigation with IllegalStateException and returns defensive copies of stored record states.

Read-only queries, navigation, help, exit and appearance changes do not add history entries or invalidate redo. Their isReadOnly() declarations also bypass domain-record saving. A failed record save does not prevent navigation, Help or normal exit; shutdown preference saving remains separate. A new successful record mutation after undo discards the undone branch. Explicit whole-model replacement with setAddressBook() starts fresh history; transaction publication uses its separate API to retain it.

History is session-only and is not serialized. Restarting loads the most recently saved record state with no undo or redo available. Preferences, search filters, window geometry and command-input history are outside record history. The existing shell refreshes summaries, groups, holdings and loan history; when undo removes a displayed exact record, it returns to the corresponding filtered directory. No undo/redo buttons or new shortcuts are provided.

Retention limit and command flow

After twelve successful record changes, only history states s2 through s12 and the ten actions between them remain in the current history. The earliest reachable state is s2: ten undos reach position 0, and ten redos can return to s12. These limits apply to reversible commands, not the number of records. Older history values referenced transiently during a transaction can share stored history states; the bound applies to the history retained by each model. A failed save cannot evict entries from the live history.

Design considerations and verification

Complete history states keep linked member/equipment/loan data consistent and make batch restoration atomic. They cost more memory than per-command inverse operations, so retention is capped at ten changes. Inverse operations would require separate reversal logic for every command and batch failure path.

AddressBookHistoryTest covers the cap, branching, descriptions, history state isolation and invalid navigation. Command/parser tests cover syntax and empty history. UndoRedoIntegrationTest verifies identity and loan restoration, lifecycle changes, exact saved states, ten undos/redos, restart behavior and failed-save retries. Shell tests exercise the real command box, preserved filters, missing details, loans and error feedback. ModelManagerTest checks history availability inside synchronous collection listeners, unchanged-record history transitions, and rollback when replacement records are invalid.

Completion execution details

The controller is created by CommandBox and retained through the field's registered callbacks, rather than a CommandBox member field. Static vocabulary uses no model reads. Record-value suggestions read the live root synchronously on the FX thread and observe member/equipment collection changes with weak listeners. These notifications invalidate record candidates after mutations, undo/redo and reload; rejected mutations and pure queries leave those collections unchanged. Cached record cycles check root identity cheaply, while unchanged candidates cycle without copying or rescanning records. Loan history and transaction validation are outside suggestion reads.

Atomic-save access policy

AtomicFileWriter creates an empty sibling candidate and restricts its POSIX mode or ACL before writing any serialized data. On ACL filesystems, inherited grants are replaced with an owner-only ACL. Only after writing/flushing succeeds does it copy the final destination policy before the atomic move. Existing POSIX owner/group/mode and ACL-view owner/ACL are retained; failure to read or apply that policy aborts without replacing the destination. POSIX files with no write bits and DOS read-only files explicitly reject saving. This policy is separate from effective access checks: no preliminary isWritable() check can guarantee a later replacement. New files retain the restricted owner-only policy where POSIX or ACL views are supported. Other metadata is not copied. No serialization schema changes are involved.

Command-word aliases and casing

Standalone s/o and d/o tokens, ignoring case, remain literal field text in argument parsing and completion. Other whitespace-delimited markers remain reserved, including unknown markers in notes. The shared argument parser rejects extra input to no-argument commands with This command takes no arguments. and the leaf parser appends its usage. Appendix: Requirements

Product scope

Laplace is a local, single-user desktop application for a CCA EXCO member to manage the CCA's members, equipment inventory, and equipment loans.

Target user profile:

  • Is a CCA EXCO member responsible for maintaining member records and tracking equipment issued to members.
  • Needs to distinguish individual equipment units, identify their current holders, and record issue and return dates.
  • Maintains the records on their own computer; members are recorded entities, not additional application users.
  • Can type quickly, prefers commands to repeated mouse interactions, and is comfortable learning a small command vocabulary.
  • Wants a consolidated view of membership, inventory, and equipment responsibility during day-to-day club operations.

Value proposition: Laplace helps a CCA EXCO member keep member details, equipment records, and loans in one place. Commands support quick record entry and lookup, while linked member and equipment views show who holds each item. Availability checks prevent double assignments, reducing confusion and manual cross-checking during equipment issue and return.

Requirements baseline and scope:

The requirements below distinguish the delivered product from proposals. A future story records an intended capability without committing the release to implementing it. Current commands and limitations are specified in the User Guide; implementation sections describe the shipped design.

  • MVP baseline: Add, list, view, and delete members and equipment; identify members by NUS ID and equipment by a generated UUID; issue and return individual items; show holdings and holders; validate input and preserve consistency on failure.
  • Delivered beyond the baseline: Member/equipment editing and restoration, substring search, filters and sorting, inventory group summaries, batch creation/issue/return, handover condition recording, and retained loan histories are implemented. Undo/redo retains up to ten changes per session.
  • Future proposals: Import/export with preview, restoring a complete exported backup, archival, approximate-name matching, and a browsable action audit remain unimplemented. They are labeled Future in the stories and use cases below.
  • Deletion and retention: Members and equipment are soft-deleted only without open loans. Records and closed history are retained; restoration has no time limit. This supersedes the original permanent-deletion and proposed 30-day recovery policies. The Loans tab and entity details show completed loan history.
  • Single-user boundary: Proposed import/export would support the same user's local records and backups. Sharing an exported dataset with another operator is outside regular product operations. Shared datasets, concurrent users, and member self-service are outside scope.

Non-Functional Requirements

These are acceptance targets for the intended product, not measurements of the current implementation. Product constraints are adapted from the course project constraints; development-process requirements such as incremental delivery are not product NFRs.

  1. NFR01 — Platform compatibility: The release shall launch and support its documented operations on Windows, Linux, and macOS with Java 25 as the only installed Java version.
  2. NFR02 — Portable distribution: The application shall run from a single downloadable JAR without an installer or separate installation of dependencies other than Java. The JAR shall not exceed 100 MB.
  3. NFR03 — Local operation: Member, equipment, loan, and local backup operations shall work without a network connection, remote server, or external account. Each dataset belongs to one local operator; shared or concurrent access is unsupported.
  4. NFR04 — Editable storage: Persistent records shall use local, human-editable text files without a DBMS. Valid edits made while the application is closed shall load on restart; invalid files shall produce a diagnostic rather than be silently accepted.
  5. NFR05 — Keyboard operation: Every documented record-management operation shall be completable with keyboard input alone. Users shall not need mouse actions to submit commands, inspect results, or correct input.
  6. NFR06 — Display compatibility: At 1920×1080 with 100% or 125% scaling, essential controls and feedback shall not overlap or be clipped. At 1280×720 with 150% scaling, every operation and its result shall remain accessible, using scrolling where necessary.
  7. NFR07 — Capacity and response time: With 1,000 members, 5,000 equipment items, and 10,000 loans on a computer with a four-core CPU, 8 GB RAM, and an SSD, at least 95 of 100 executions of each core add, list, exact lookup, delete, issue, and return operation shall display a result within two seconds of submission. Measure after startup, with valid data and no competing intensive workload; include local saving for mutations. Startup with the same dataset shall complete within ten seconds.
  8. NFR08 — Atomicity and durability: After a successful mutation and normal shutdown, restarting shall recover the same records and loan relationships. Validation or reported save failures shall not leave partially updated member, equipment, or loan data. A failed file replacement shall preserve the last valid saved dataset. The same guarantee applies to batch and undo/redo operations as a whole, and to future import/restore operations.
  9. NFR09 — Consistent feedback: Every rejected command shall identify the first detected problem and provide an accepted format or corrective action. Input errors shall not terminate the application, and the submitted command shall remain available for correction. Success and error messages shall be distinguishable by text, without relying on color alone.
  10. NFR10 — Data confidentiality: Laplace shall not transmit member details or inventory records over the network. Diagnostic logs shall omit member names, phone numbers, email addresses, and raw commands containing those values. Local text data and user-created exports rely on the operating system's file access controls; application-level encryption is not promised.
  11. NFR11 — Read-only navigation: Directory, detail, loan-filter, Help and Exit operations shall remain available when record storage cannot be written. They shall not save domain records or consume undo steps.

Glossary

Term Definition
CCA Co-Curricular Activity; the club or student organization whose records the operator manages.
EXCO member / operator A member of the CCA's executive committee who operates their own Laplace installation.
Member record The stored identity and contact details of a person in the CCA. Being recorded does not give that person application access.
NUS ID A member's unique, immutable identifier in Laplace. The MVP accepts one ASCII letter, seven digits, and an optional final ASCII letter; comparison ignores case and storage uses uppercase.
Equipment item / unit One individually tracked physical object. Identical models are separate items, each with its own identifier.
UUID Universally unique identifier. Laplace generates one immutable UUID for each equipment item; names and descriptions are not equipment identifiers.
Category A broad grouping recorded on an equipment item, such as cameras or sports equipment. One category can contain different equipment types.
Equipment type A particular kind or model of equipment, such as a Canon EOS R50 camera. Physical units with the same normalized category and name form an inventory group, which inventory summaries use.
Condition The recorded physical state of an item: GOOD, FAIR, DAMAGED, or UNDER_REPAIR in the MVP.
Availability A derived state, never an independently stored value. Deleted units are UNAVAILABLE. For active units, an open loan means ASSIGNED; otherwise GOOD/FAIR means AVAILABLE and DAMAGED/UNDER_REPAIR means UNAVAILABLE.
Equipment loan / assignment A relationship between one member and one equipment item, with assignment, expected return, and optional actual return dates. A member may have several loans; an item has at most one open loan.
Open loan / outstanding equipment A loan with no actual return date, or the item covered by that loan. The associated member remains responsible until return is recorded.
Closed loan A loan whose actual return date has been recorded. It no longer determines a current holder.
Holder The member referenced by an item's open loan. An item without an open loan has no current holder.
Assignment date The date the item was issued; it must be a real calendar date no later than the computer's local date.
Expected return date The due date, on or after assignment. Reaching it does not automatically record a return.
Actual return date The recorded date of return, from the assignment date through the computer's local date, inclusive.
Overdue loan An open loan whose expected return date is before the computer's local date. This definition does not imply automatic notifications.
Active record A member or equipment record whose deletion flag is false. All-record lists also display retained deleted records; active-only searches exclude them. Active equipment can still be assigned or unavailable.
Archive A future proposal for setting aside an inactive member while preserving history. Archival is not implemented and is distinct from the shipped soft-delete/restore operations.
Delete Soft deletion: marking a retained record deleted, allowed only without open loans. Its identity remains reserved, and its details and closed history stay stored.
Restore Reactivating a retained deleted member or equipment unit without a time limit, preserving identity and history.
Retained record An active or soft-deleted member/equipment record still stored in the dataset. Soft-deleted records can be restored without changing their identity or closed loan history.
Inventory group A derived group of physical equipment units with matching normalized category and name. Group totals distinguish available, assigned, unavailable, and deleted units; a group is not a separately persisted equipment identity.
Transaction candidate / candidate In transaction discussions, the isolated model copy on which a mutation runs, created by Model.createTransactionSnapshot(). It has independent mutable collection containers and is discarded on failure. Autocomplete uses completion candidates to mean suggested input values instead.
Transaction A record-changing operation staged on a candidate, persisted atomically, then published to the live model. Batches and undo/redo succeed or fail as a whole.
Publication Updating the existing live observable model with the successfully saved candidate's records and matching session history. It happens after persistence succeeds.
History state A private stored copy of the records retained for undo/redo. A selected history state is copied into a candidate for navigation; it is not the live model or a user-exported file.
Backup snapshot A proposed complete local export of persistent records and their relationships for later recovery. Export and restore-backup are Future capabilities (US03, US40, UC07); this term does not denote a transaction candidate or a session history state.
Display request An immutable navigation intent returned with command feedback. The UI uses it to choose a directory, group, or detail view without parsing message text. It is not persisted record data.
Compact UUID label A shortened UUID shown as a visual aid in an inventory group. It can collide with another label and is not a command identifier; exact-unit commands use the full UUID.
Atomic operation An operation whose changes succeed together or leave the preceding consistent state intact.
MVP Minimum viable product; the delivered baseline capabilities, which are a subset of the full requirements recorded here.
