Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below is an inherited AB3 example using delete 1. That command is now rejected; see command routing and legacy compatibility for current behavior.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

MainWindow owns navigation, the command pipeline and coalesced model refresh subscriptions. Its member/equipment directories, summaries, details and loan panel are read-only views. Most panels extend UiPart and load FXML; EquipmentGroupPanel and CommandPreview compose JavaFX controls directly. The inherited person panel remains an internal compatibility component, outside the supported navigation.

DisplayRequest carries typed navigation intent. Directory requests with no query preserve criteria; explicit list commands reset them. InventoryGroups.Group derives normalized category/name groups and keeps separate retained and matching unit lists. Groups are never persisted. Selecting a group does not choose an arbitrary UUID; physical-unit selection routes equipment view uuid/... through the same pipeline as typed input. Refreshes preserve exact identities and recompute group membership after edits, loans, deletion and restoration. The group panel shares one scrolling surface with unit details.

CommandPreview copies exact plain text or prepares CommandBox; neither action executes a mutation. The command catalog supplies examples and explicit completion. Input history is bounded to 100 session entries. ResultDisplay keeps full feedback behind a compact, expandable view. Related-record links use identity-based commands. LoanPanel filters open and completed loans by stable member/equipment IDs. Only open loans derive urgency from expected return dates and an injectable clock, and offer a return shortcut for explicit review and submission. Completed rows show recorded conditions and return dates. Loan urgency refreshes on commands, data changes and opening the Loans tab; there is no background midnight timer.

LaplaceTheme.css defines shared looked-up colors; component styles refer to these tokens. A dark style class changes the palette for both windows, including table selection, feedback and command previews. ModeCommand updates only GuiSettings.darkMode and returns an unchanged display request. Its isReadOnly() flag means no domain-record persistence; preferences are saved by the existing shutdown path. Missing darkMode in earlier preference JSON defaults to false. Window geometry and appearance are preserved together; equipment/member/loan schemas are unchanged.

Tests exercise actual FXML/CSS on the shared JavaFX thread, command/storage routing, identity preservation, filter scope, date boundaries, clipboard text, theme changes and preference compatibility. UI snapshots are written under build/reports/laplace for visual review. Command text and identifiers use bundled IBM Plex Mono. LaplaceFonts registers those faces once and applies interface fonts by full face name: Helvetica/Helvetica Bold, then Arial/Arial Bold or Segoe UI/Segoe UI Bold when unavailable, with a system fallback. This bypasses JavaFX family/weight substitution that can clip bold interface glyphs. The helper owns interface sizes and weights; CSS owns colors, layout and monospace text. It observes new children, graphics and label style changes so dynamic rows and headings receive the same treatment. Tests check resolved face names as well as rendered layouts; checking only a Bold style is insufficient.

The feedback heading displays only Last result; the box carries neutral/success/error color, and assistive text contains the status plus the entire message. Ready command previews say Press Enter to execute (ready); templates say Replace uppercase placeholders (template). Copy and Use command still never execute a command.

Tab completion

MainWindow supplies the live read-only address book to CommandBox. CompletionService computes replacement ranges and ordered candidates without calling logic, history or storage. Command constants and shared search prefix constants define all accepted routes and fields. Search enum options follow DirectoryQuery; dates, numeric counts, new member IDs and free-form notes are entered manually. Batch loan completion replaces only the active UUID entry and excludes neighboring identities. CompletionController owns cycling and resets after input, caret, focus or model changes. Enter retains the ordinary parser and transactional command path. Tests compare family completion to parser routes, exercise real JavaFX events, and load production classes from the packaged JAR. Gradle enforces 100% instruction, line and branch coverage for the feature, including its UI wiring. See Testing.

Command routing and legacy compatibility

LogicManager.execute() first calls AddressBookParser.parseCommand(). The root parser accepts member, equipment, and loans, delegating to their family parsers and then the appropriate leaf parser (for example, EquipmentCommandParser and EquipmentAddCommandParser). It also accepts help and exit. Family and leaf parsers remain responsible for validating subcommands and arguments.

The retired top-level words add, edit, delete, clear, find, and list now reach the existing unknown-command branch and throw ParseException("Unknown command."). In particular, list members is rejected; the supported command is member list. Rejection occurs before a command is constructed or executed, before a transaction snapshot is created, and before storage is called.

For supported commands, LogicManager executes transactional mutations on an isolated model snapshot, saves that candidate state, and publishes it to the live root only after saving succeeds. Commands marked isReadOnly() return without saving. This retirement does not change those execution rules.

AddressBook is still the shared root for persons, members, equipment, and loans. Its name and the getAddressBook()/saveAddressBook() APIs do not identify disposable person-only behavior. Existing JSON persons data is retained and round-trips when supported commands save. Person value classes used by members, legacy command/parser implementations and their unit tests, and the legacy UI panel remain for a separate dependency-aware cleanup. Removing public routes does not remove stored records.

Model component

API : Model.java

Equipment and loan model

The following diagram shows the equipment-related subset of the current model. Member/person collections, preferences, JavaFX collection wrappers and interfaces are omitted to keep its scope clear. Solid arrows show stored references; the dashed loan-to-equipment arrow describes UUID resolution, not an object reference stored inside Loan.

AddressBook creates equipment/loan containers lazily, hence the 0..1 multiplicities. A null container means an empty collection to callers. The 0..* multiplicity at each collection end of the value associations accounts for immutable objects shared across transaction snapshots; it does not mean one physical unit has several UUIDs. Equipment collections hold distinct UUIDs, and editing replaces a value at its existing position. Ordinary associations are used instead of composition because immutable values can outlive or be shared by their containers.

Relationship or rule Meaning in a valid root dataset
Loan → equipment Each loan's equipmentUuid resolves to exactly one retained equipment record. A unit can have zero or more historical loans, with at most one open loan.
Loan → member (omitted from diagram) Each loan's memberNusId resolves to one retained member. A member may have multiple open or closed loans.
Identity and details UUID identifies a physical unit. Name/category determine a derived inventory group; matching descriptions do not merge identities.
Lifecycle Deleted records retain UUIDs, details and closed loans. Open loans cannot reference deleted equipment or deleted members.
Availability ModelManager returns UNAVAILABLE for deleted units; otherwise the calculator returns ASSIGNED for an open loan, AVAILABLE for GOOD/FAIR, and UNAVAILABLE for DAMAGED/UNDER_REPAIR.

Availability, holders and inventory totals are derived, never persisted as independent fields. AvailabilityCalculator only accepts condition and open-loan state; the deletion check belongs to ModelManager. AddressBook validates cross-record references, while UniqueLoanList enforces the one-open-loan-per-unit rule. UniqueEquipmentList checks UUID uniqueness and identity-preserving replacement. These responsibilities keep editing and restoration from breaking loan references.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Adding multiple physical equipment units

EquipmentAddCommandParser accepts optional count/ through LaplaceArgumentParser, retaining its left-to-right validation and duplicate-prefix checks. Counts default to 1 and must be ASCII digits with a numeric value from 1 to EquipmentAddCommand.MAX_COUNT (100). The command constructor also validates the range for direct callers. The cap bounds accidental bulk creation and feedback size.

EquipmentAddCommand reserves all identities before inserting units. A local set prevents duplicate UUIDs within the batch; Model.hasEquipment excludes already-stored UUIDs. Each unit has a bounded 100-attempt generation budget. The command computes an advisory duplicate-description warning against the pre-batch records, then inserts units into the candidate model supplied by LogicManager.

The existing transactional path saves that candidate once and publishes only after success. Generation failure leaves the candidate untouched; insertion or persistence failure discards the candidate without changing live records. No quantity field, batch entity, persistence migration, or new model API is added.

Count 1 preserves existing feedback and equipmentDetails(uuid) navigation. Larger batches report all new UUIDs and return DisplayRequest.equipment(DirectoryQuery.all()), resetting prior filters/sorting so the newly created units can be found. Availability remains derived from each unit's condition/loans.

Equipment-add parsing

The parsing sequence below traces a valid equipment add ... count/2 request and leaf-parser rejection. AddressBookParser selects the family, EquipmentCommandParser selects the operation, and EquipmentAddCommandParser applies the shared grammar and validators before constructing the command. Parsing is separate from UUID generation and does not access or mutate the live model.

The diagram omits shared-validator lifelines and command-constructor normalization calls. The parser returns a command; it does not execute it. Missing/unknown family or subcommand errors stop earlier in the chain. Neither a parser failure nor invalid count creates a transaction snapshot or saves data.

Equipment-add execution and publication

The next sequence starts after successful parsing. Model.createTransactionSnapshot() creates a new ModelManager with independent collection containers. Immutable entity values may be shared until a command replaces them. EquipmentAddCommand.execute(candidate) prepares the complete batch before inserting any unit. The diagram abbreviates the root/collection delegation and the repeated read-only UUID checks; these occur on the candidate, not on the live model.

The CommandResult exists before saving, but LogicManager returns it to the UI only after successful persistence and publication. Count 1 requests exact-unit details; larger batches request the full equipment directory. Observable refreshes resolve current data by identity after publication.

The shown failure alternative is an IOException during saving. Serialization/write/replacement failure prevents publication; partial writes affect only a private temporary file, and unsupported atomic replacement fails rather than falling back to truncation. Temporary-file cleanup is attempted on failure. The existing data file remains intact; a first failed save need not leave a data file. Validation, UUID-generation and command-execution failures occur before the save call and are omitted from the successful execution path shown. A failure after candidate insertion still discards that candidate, so a later successful command cannot accidentally save a failed batch.

Editing, soft deletion and restoration use the same snapshot/save/publish boundary with different command bodies. Equipment list/search are read-only and do not follow this mutation sequence. These diagrams describe a single-user command transaction, not concurrent-writer coordination or an undo/redo implementation.

Equipment editing, deletion and restoration

Each Equipment is an immutable physical unit. EquipmentEditCommand builds a replacement with the stored UUID and any supplied details. AddressBook.setEquipment permits only active-to-active edits; UniqueEquipmentList.setEquipment checks UUID equality and replaces the value at the same index. Name/category changes affect derived inventory groups, never sibling units. Unspecified legacy text is retained verbatim; new text uses equipment-add validation. Notes can be cleared explicitly.

AddressBook.removeEquipment now marks a unit deleted after checking that no open loan exists. restoreEquipment clears the flag. Both retain UUID, details and closed loans. This supersedes the historical scaffold's permanent deletion. Member and equipment restoration have no time limit.

Lifecycle is separate from condition and loan status. Editing condition while loaned is allowed: ASSIGNED remains derived from the open loan; on return the edited condition controls availability. Deleted units derive UNAVAILABLE, cannot receive open loans, and are excluded from inventory totals. Root loan validation applies this invariant both to new loans and complete dataset replacement/loading.

JsonAdaptedEquipment writes a boolean deleted. An absent flag defaults to false for earlier files; explicit null and non-boolean values fail loading. Closed loans may reference deleted equipment. All maintenance commands are transactional: execute against a snapshot, save atomically, then publish. No-change/rejected edits and failed writes leave live state and previously saved bytes unchanged.

Directory queries share DirectoryQuery.Status across members and equipment. Equipment search defaults to active; status/deleted|all exposes retained units. List resets to all states and does not save. Cards label deleted units; details show lifecycle state and a restore command. Edit/restore navigate to the same UUID, retaining query criteria even if that unit no longer matches. Total counts include deleted units; availability counts and inventory groups include active units only. The Loans tab and entity details show the retained completed loan history.

[Proposed] Undo/redo feature

The following inherited AB3 proposal uses retired person commands as examples. It is not implemented Laplace behavior and needs redesign for the current domain before implementation.

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

The redo command does the opposite — it calls Model#redoAddressBook(), which shifts the currentStatePointer once to the right, pointing to the previously undone state, and restores the address book to that state.

Note: If the currentStatePointer is at index addressBookStateList.size() - 1, pointing to the latest address book state, then there are no undone AddressBook states to restore. The redo command uses Model#canRedoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.

Step 5. The user then decides to execute the command list. Commands that do not modify the address book, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

Step 6. The user executes clear, which calls Model#commitAddressBook(). Since the currentStatePointer is not pointing at the end of the addressBookStateList, all address book states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David … command. This is the behavior that most modern desktop applications follow.

Appendix: Requirements

Product scope

Laplace is a local, single-user desktop application for a CCA EXCO member to manage the CCA's members, equipment inventory, and equipment loans.

Target user profile:

  • Is a CCA EXCO member responsible for maintaining member records and tracking equipment issued to members.
  • Needs to distinguish individual equipment units, identify their current holders, and record issue and return dates.
  • Maintains the records on their own computer; members are recorded entities, not additional application users.
  • Can type quickly, prefers commands to repeated mouse interactions, and is comfortable learning a small command vocabulary.
  • Wants a consolidated view of membership, inventory, and equipment responsibility during day-to-day club operations.

Value proposition: Laplace helps a CCA EXCO member keep member details, equipment records, and loans in one place. Commands support quick record entry and lookup, while linked member and equipment views show who holds each item. Availability checks prevent double assignments, reducing confusion and manual cross-checking during equipment issue and return.

Requirements baseline and scope:

These requirements consolidate the team's project notes: Week 4 (direction), Week 5 (all 41 user stories), and Week 6 (MVP and feature specifications). They describe intended behavior, including requirements beyond the MVP; they do not claim that every feature is implemented. Where the earlier schema differs from the later Feature Specifications, the latter defines the MVP baseline.

  • MVP baseline: Add, list, view, and delete members and equipment; identify members by NUS ID and equipment by a generated UUID; issue and return individual items; show holdings and holders; validate input and preserve consistency on failure.
  • Broader requirements: Editing, archiving, recovery, import/export, search and filtering, summaries, batch operations, condition recording at handover, histories, and undo/redo remain documented below even if they are not delivered this semester.
  • Deletion and retention: Members and equipment are soft-deleted only without open loans. Records and closed history are retained; restoration has no time limit. This supersedes the original permanent-deletion and proposed 30-day recovery policies. The Loans tab and entity details show completed loan history.
  • Single-user boundary: Import/export supports the same user's local records and backups. The earlier idea of handing a snapshot to another EXCO member is retained as a considered use of export, but is excluded from the course product's regular operations. Shared datasets, concurrent users, and member self-service are outside scope.

Use cases

For all use cases, the system is Laplace and the actor is the CCA EXCO member operating their local installation. The application is running with a valid dataset unless stated otherwise. The member borrowing equipment is not a second system actor. MSS means main success scenario. Extension labels refer to the MSS step at which the alternative occurs; each extension states where execution resumes or ends.

For every data-changing use case, a validation failure leaves all records unchanged. If saving fails at the final update step, Laplace reports that the operation was not saved and retains the preceding consistent state; the use case ends unsuccessfully. Success is reported only after persistence succeeds. These rules also apply to proposed future operations.

UC01: Register a member

Scope: MVP. Related stories: US04, US13, US41, US45.

MSS

  1. The EXCO member provides the new member's NUS ID, name, phone number, and email.
  2. Laplace validates the details and checks that the normalized NUS ID is not already registered.
  3. Laplace saves the member and shows the stored details.

Use case ends.

Extensions

  • 2a. Required details are missing or invalid.
    • 2a1. Laplace identifies the invalid input and explains the accepted format.
    • Use case resumes at step 1.
  • 2b. The NUS ID already exists, ignoring letter case.
    • 2b1. Laplace rejects the duplicate and identifies the existing member.
    • Use case resumes at step 1.

Names, phone numbers, or email addresses shared by different NUS IDs do not by themselves constitute duplicates.

UC02: Register physical equipment units

Scope: Implemented. Related stories: US14, US15, US17, US41, US45.

MSS

  1. The EXCO member provides the units' name, category, condition, optional notes, and optional count.
  2. Laplace validates the details and count (default 1, range 1-100), then reserves a distinct UUID per unit.
  3. Laplace saves all units in one transaction and reports their UUIDs and derived availability. One unit opens details; a batch opens the unfiltered equipment directory.

Use case ends.

Extensions

  • 2a. Required details are missing or invalid.
    • 2a1. Laplace explains what needs correcting.
    • Use case resumes at step 1.
  • 2b. Laplace cannot generate a unique identifier.
    • 2b1. Laplace reports the failure without adding any units.
    • Use case ends.

Matching descriptions are permitted: each physical unit receives its own UUID. An item in DAMAGED or UNDER_REPAIR condition may be registered but is unavailable for issue.

UC03: Issue equipment to a member

Scope: MVP. Related stories: US06, US16, US24, US25, US27–US29, US43, US44.

MSS

  1. The EXCO member requests the intended member's details by NUS ID and the equipment inventory.
  2. Laplace shows the member's details and current holdings, and the equipment with its availability and UUIDs.
  3. The EXCO member requests assignment of one item to that member, supplying the assignment and expected return dates.
  4. Laplace validates the references, availability, and dates, then saves an open loan and shows the updated holder and holdings.

Use case ends.

Extensions

  • 2a. The member identifier is invalid or no matching member exists.
    • 2a1. Laplace explains the problem.
    • Use case resumes at step 1.
  • 2b. No equipment is available for issue.
    • 2b1. Laplace shows that no suitable item is available.
    • Use case ends.
  • 4a. A supplied identifier is invalid or does not identify an existing record.
    • 4a1. Laplace identifies the invalid or missing reference.
    • Use case resumes at step 3.
  • 4b. The item already has an open loan, or its condition is DAMAGED or UNDER_REPAIR.
    • 4b1. Laplace refuses the assignment and gives the reason, including the current holder when applicable.
    • Use case resumes at step 3.
  • 4c. A date is invalid, the assignment date is after today, or the expected return date precedes assignment.
    • 4c1. Laplace explains the violated date rule.
    • Use case resumes at step 3.

UC04: Record an equipment return

Scope: MVP. Related stories: US17, US26–US28, US41, US44.

MSS

  1. The EXCO member requests an item's details by UUID.
  2. Laplace shows the item, current holder, assignment date, and expected return date.
  3. The EXCO member requests that the item be recorded as returned and supplies the actual return date.
  4. Laplace validates and saves the return, closes the loan, removes the current holder, and updates availability and the member's holdings.

Use case ends.

Extensions

  • 2a. The UUID is invalid or no item matches it.
    • 2a1. Laplace explains the problem.
    • Use case resumes at step 1.
  • 2b. The item has no open loan.
    • 2b1. Laplace reports that the item is not currently assigned.
    • Use case ends.
  • 4a. The supplied item reference is invalid, missing, or has no open loan, including an already recorded return.
    • 4a1. Laplace rejects the request and explains the problem.
    • Use case resumes at step 1.
  • 4b. The actual return date is invalid, before assignment, or after today.
    • 4b1. Laplace explains the allowed date range.
    • Use case resumes at step 3.

Passing the expected return date never closes a loan automatically. A return after the expected date is valid. After return, only items in GOOD or FAIR condition become available.

UC05: Delete an erroneous member or equipment record

Scope: MVP. Related stories: US05, US09, US16, US19, US41.

MSS

  1. The EXCO member requests the member list or equipment list, according to the kind of record to remove.
  2. Laplace shows the requested records and their identifiers.
  3. The EXCO member requests deletion of one record using its NUS ID or UUID, respectively.
  4. Laplace verifies that the record has no open loans, marks it deleted while retaining its details and closed loans, and confirms the deletion.

Use case ends.

Extensions

  • 2a. The requested list is empty.
    • Use case ends.
  • 4a. The identifier is invalid or no matching record exists.
    • 4a1. Laplace reports the problem without deleting anything.
    • Use case resumes at step 3.
  • 4b. The member still holds equipment, or the equipment item is currently assigned.
    • 4b1. Laplace refuses deletion and explains that the outstanding items must first be returned.
    • Use case ends without deletion. The EXCO member may complete UC04 and start UC05 again.

Already-deleted records are rejected without a save. To recover a record, find it with a status/deleted search, then issue member restore nus/NUS_ID or equipment restore uuid/UUID. Laplace clears the flag, saves and opens its details. Unknown/already-active records fail without changes. Recovery has no time limit; equipment condition is preserved. Closed history remains retained throughout.

UC05a: Edit equipment details

Scope: Implemented. Related story: US18.

  1. The EXCO member views a physical unit and supplies its UUID with one or more edited details.
  2. Laplace validates the fields and requires an active unit and an actual change.
  3. Laplace replaces the details under the same UUID, saves and displays the updated unit.

Invalid fields, unknown UUIDs, deleted units and no-change edits leave the dataset unchanged. An open loan permits details/condition edits and retains its reference; save failure preserves the previous state.

UC06: Import records after reviewing a preview

Scope: Future. Related stories: US01, US02, US13, US41.

MSS

  1. The EXCO member requests import from a local member and equipment data file.
  2. Laplace reads and validates the file, showing a preview of records to add, change, or reject without altering current data.
  3. The EXCO member reviews a preview with no unresolved errors and confirms the import.
  4. Laplace applies and saves the previewed changes as one operation and reports the result.

Use case ends.

Extensions

  • 2a. The file is missing, unreadable, or in an unsupported format.
    • 2a1. Laplace explains why it cannot produce a preview.
    • Use case resumes at step 1.
  • 2b. Records are invalid, identifiers conflict, or the proposed changes would break loan references.
    • 2b1. Laplace identifies the affected records and reasons and prevents confirmation until they are resolved.
    • Use case resumes at step 1 after the EXCO member corrects or chooses another file.
  • 3a. The EXCO member cancels.
    • Use case ends with current data unchanged.
  • 4a. The source file or current dataset has changed since the preview.
    • 4a1. Laplace invalidates the old preview without applying it.
    • Use case resumes at step 2.

UC07: Restore a complete backup

Scope: Future. Related stories: US03, US40, US41. Precondition: The EXCO member has a previously exported complete snapshot. Laplace can accept a restore request even if its normal data file cannot be loaded.

MSS

  1. The EXCO member selects a local snapshot for restoration.
  2. Laplace validates the complete snapshot and explains that restoration will replace the current dataset.
  3. The EXCO member confirms replacement.
  4. Laplace restores and saves the snapshot as one operation, then shows the restored records.

Use case ends.

Extensions

  • 2a. The snapshot is unreadable, incompatible, incomplete, or contains invalid records or broken loan references.
    • 2a1. Laplace rejects it and explains the problem without replacing current data.
    • Use case resumes at step 1.
  • 3a. The EXCO member cancels replacement.
    • Use case ends with current data unchanged.
  • 4a. The snapshot has changed since validation.
    • 4a1. Laplace discards the previous validation result without replacing current data.
    • Use case resumes at step 2.

UC08: Undo a mistaken change

Scope: Future. Related stories: US37, US38, US41.

MSS

  1. The EXCO member requests undo of the most recent successful data-changing action.
  2. Laplace restores and saves the preceding consistent state, including linked records, and identifies the undone action.
  3. The EXCO member inspects the restored records.

Use case ends.

Extensions

  • 2a. There is no action available to undo.
    • 2a1. Laplace explains that no undo is available and leaves the data unchanged.
    • Use case ends.
  • 3a. The EXCO member decides the undo was a mistake and requests redo before any new data-changing action.
    • 3a1. Laplace reapplies and saves the undone action and shows the resulting records.
    • Use case ends.
  • 3b. The EXCO member requests redo after a new successful data-changing action has invalidated it.
    • 3b1. Laplace explains that no redo is available and leaves the current data unchanged.
    • Use case ends.

A new successful data-changing action after undo invalidates redo. Read-only actions and failed commands do not add undo entries or invalidate redo. The future retention policy must support restoring any deleted records covered by undo.

Non-Functional Requirements

These are acceptance targets for the intended product, not measurements of the current implementation. Product constraints are adapted from the course project constraints; development-process requirements such as incremental delivery are not product NFRs.

  1. NFR01 — Platform compatibility: The release shall launch and support its documented operations on Windows, Linux, and macOS with Java 25 as the only installed Java version.
  2. NFR02 — Portable distribution: The application shall run from a single downloadable JAR without an installer or separate installation of dependencies other than Java. The JAR shall not exceed 100 MB.
  3. NFR03 — Local operation: Member, equipment, loan, and local backup operations shall work without a network connection, remote server, or external account. Each dataset belongs to one local operator; shared or concurrent access is unsupported.
  4. NFR04 — Editable storage: Persistent records shall use local, human-editable text files without a DBMS. Valid edits made while the application is closed shall load on restart; invalid files shall produce a diagnostic rather than be silently accepted.
  5. NFR05 — Keyboard operation: Every documented record-management operation shall be completable with keyboard input alone. Users shall not need mouse actions to submit commands, inspect results, or correct input.
  6. NFR06 — Display compatibility: At 1920×1080 with 100% or 125% scaling, essential controls and feedback shall not overlap or be clipped. At 1280×720 with 150% scaling, every operation and its result shall remain accessible, using scrolling where necessary.
  7. NFR07 — Capacity and response time: With 1,000 members, 5,000 equipment items, and 10,000 loans on a computer with a four-core CPU, 8 GB RAM, and an SSD, at least 95 of 100 executions of each core add, list, exact lookup, delete, issue, and return operation shall display a result within two seconds of submission. Measure after startup, with valid data and no competing intensive workload; include local saving for mutations. Startup with the same dataset shall complete within ten seconds.
  8. NFR08 — Atomicity and durability: After a successful mutation and normal shutdown, restarting shall recover the same records and loan relationships. Validation or reported save failures shall not leave partially updated member, equipment, or loan data. A failed file replacement shall preserve the last valid saved dataset. The same guarantee applies to future batch, import, restore, and undo operations as a whole.
  9. NFR09 — Consistent feedback: Every rejected command shall identify the first detected problem and provide an accepted format or corrective action. Input errors shall not terminate the application, and the submitted command shall remain available for correction. Success and error messages shall be distinguishable by text, without relying on color alone.
  10. NFR10 — Data confidentiality: Laplace shall not transmit member details or inventory records over the network. Diagnostic logs shall omit member names, phone numbers, email addresses, and raw commands containing those values. Local text data and user-created exports rely on the operating system's file access controls; application-level encryption is not promised.

Glossary

Term Definition
CCA Co-Curricular Activity; the club or student organization whose records the operator manages.
EXCO member / operator A member of the CCA's executive committee who operates their own Laplace installation.
Member record The stored identity and contact details of a person in the CCA. Being recorded does not give that person application access.
NUS ID A member's unique, immutable identifier in Laplace. The MVP accepts one ASCII letter, seven digits, and an optional final ASCII letter; comparison ignores case and storage uses uppercase.
Equipment item / unit One individually tracked physical object. Identical models are separate items, each with its own identifier.
UUID Universally unique identifier. Laplace generates one immutable UUID for each equipment item; names and descriptions are not equipment identifiers.
Category A broad grouping recorded on an equipment item, such as cameras or sports equipment. One category can contain different equipment types.
Equipment type A particular kind or model of equipment, such as a Canon EOS R50 camera. Several physical units can share a type; the future batch and summary stories refer to these units, rather than every item in a broad category.
Condition The recorded physical state of an item: GOOD, FAIR, DAMAGED, or UNDER_REPAIR in the MVP.
Availability A derived state: ASSIGNED when an open loan exists; otherwise AVAILABLE for GOOD or FAIR condition, and UNAVAILABLE for DAMAGED or UNDER_REPAIR. It is not entered independently.
Equipment loan / assignment A relationship between one member and one equipment item, with assignment, expected return, and optional actual return dates. A member may have several loans; an item has at most one open loan.
Open loan / outstanding equipment A loan with no actual return date, or the item covered by that loan. The associated member remains responsible until return is recorded.
Closed loan A loan whose actual return date has been recorded. It no longer determines a current holder.
Holder The member referenced by an item's open loan. An item without an open loan has no current holder.
Assignment date The date the item was issued; it must be a real calendar date no later than the computer's local date.
Expected return date The due date, on or after assignment. Reaching it does not automatically record a return.
Actual return date The recorded date of return, from the assignment date through the computer's local date, inclusive.
Overdue loan An open loan whose expected return date is before the computer's local date. This definition does not imply automatic notifications.
Active record A member or equipment record included in normal lists, rather than archived or deleted. Active equipment can still be assigned or unavailable.
Archive A proposed operation that removes an inactive member from the active list while preserving their record and history.
Delete Marking a retained record deleted, allowed only without open loans. Its identity, details and closed history remain stored.
Restore Reactivating a retained deleted member or equipment unit without a time limit, preserving identity and history.
Snapshot A complete local export of Laplace's persistent records and their relationships at a point in time, used as a backup. It differs from importing selected member or equipment records.
Fuzzy search Proposed matching of incomplete or approximate text against records; distinct from the MVP's exact identifier lookup.
Atomic operation An operation whose changes succeed together or leave the preceding consistent state intact.
MVP Minimum viable product; the Week 6 baseline, which is a subset of the full requirements recorded here.

Appendix: Instructions for manual testing

Given below are instructions to test the app manually.

Note: These instructions only provide a starting point for testers to work on; testers are expected to do more exploratory testing.

Launch and shutdown

  1. Initial launch

    1. Download the JAR file and copy it into an empty folder.

    2. In that folder, run java -jar Laplace.jar with Java 25.
      Expected: The GUI opens in light mode with sample members, grouped equipment and open loans.

  2. Saving window preferences

    1. Resize the window to an optimal size. Move the window to a different location. Close the window.

    2. Relaunch with java -jar Laplace.jar.
      Expected: The most recent window size and location are retained.

Known packaging limitation: The current fat JAR contains Intel macOS JavaFX native libraries. An Apple Silicon launch without the JDK's bundled JavaFX fails with an incompatible native architecture; using a JavaFX-enabled JDK can mask this. Resolve and verify architecture-compatible packaging before releasing to users with a plain ARM64 Java 25 installation. GUI tests use a separate matching native test runtime, so a green test suite alone does not establish distributable-JAR portability.

Grouped equipment, command assistance and appearance

Use a separate empty writable JAR folder. Keep any real dataset untouched.

  1. Run equipment add name/UI Camera category/Photo condition/GOOD count/4. Expect one group containing four distinct UUIDs. Expand/copy Last result to capture all four. Open the group and select one unit; Copy UUID must copy its complete UUID. Register another matching unit; expect five units in the same group.
  2. Edit one UUID with equipment edit uuid/UUID condition/DAMAGED, then search with equipment search availability/available. The group must show matching versus retained counts; Show all units reveals the damaged sibling. Directly view that UUID and check exact selection. Uncheck Show all units: the table narrows again, the exact unit details remain visible, and a message explains that the selected unit is outside the table filter.
  3. Rename the damaged unit, delete it, then restore it with the documented equipment commands. Expect regrouping without UUID changes. Check deleted records never inflate available counts.
  4. Open a member's details, copy contact fields, and use a related equipment link. Switch tabs and use Back to results. The previous filter persists until Reset search or a list command.
  5. Use a command preview. Expect only input preparation; review and press Enter. Test history up/down with an unfinished draft, Ctrl+Space completion, Escape dismissal and keyboard focus navigation.
  6. Open Loans. Verify due/overdue labels against the computer's local date and the stored due date. Prepare a return; verify the UUID/date and that the loan remains open until submission.
  7. Run mode dark, open Help, then switch back using the header appearance button. Repeat list/table selection, previews and errors in each appearance. Exit normally and relaunch; the selected mode persists. mode sepia is rejected.
  8. Review at 1920×1080 with 100%/125% scaling and 1280×720 with 150% scaling on supported systems. Check wrapping, scrolling, visible focus and contrast. Logical-size snapshots alone do not verify OS scaling.

Tab completion across current commands

  1. In a disposable dataset, type mem and press Tab. Expected: member, with the caret at its end. Add a space and cycle with Tab, then Shift+Tab. Expected: alphabetical subcommands and reverse cycling.
  2. Try member restore n, equipment edit co, equipment add cou, and loans return co, pressing Tab after each. Expected: nus/, condition/, count/, and condition/ respectively.
  3. Try member search holding/y, equipment search availability/av and equipment search order/de. Expected: YES, AVAILABLE and desc. Enter the completed search; check the filtered directory.
  4. In loans return uuid/FIRST_UUID, PARTIAL_SECOND_UUID returned/DATE, position the caret after the partial UUID and press Tab. Expected: only that UUID is replaced; the first UUID, spacing and return date remain intact. Candidates omit UUIDs already present. Repeat with a space after the comma.
  5. Repeat a name completion with an em space (U+2003) or nonbreaking space (U+00A0) before the following phone/ field. Expected: the phone field and original separator remain, with the caret immediately after the completed name. Check the same behavior in a comma-separated UUID list.
  6. Check an untouched following field, no matching input, selected text and Shift+Tab outside a cycle. Expected: surrounding input remains intact and ordinary focus traversal remains available.
  7. Add or edit a record, then retry completion. Expected: current values are suggested. Tab alone never changes records or saves; Enter uses normal parser validation. Restart after a valid mutation and verify the saved records. New IDs, dates, numeric counts and notes remain manually entered.

Rejection of retired commands

  1. Run the JAR from a separate empty writable folder to get sample members, equipment and loans. Use only this temporary dataset for these checks. Run member list, equipment list, and loans list; record the identities and counts. Copy the saved data file for comparison if present.
  2. Enter each of add, edit 1 name/Changed, delete 1, clear, clear 3, find Alex, list, and list members. Expected: Unknown command.; the current view/selection and all records stay unchanged. An existing data file must remain byte-for-byte unchanged; rejected input must not create a data file if none existed.
  3. Run member list, equipment list, and loans list again. Expected: normal directory navigation and the same records and loan identities as before. These supported controls are separate from the rejected-input file comparison above.
  4. Restart the application. Expected: saved records still load normally. Existing JSON files with a persons array remain readable; no migration or removal of that array is required by this change.

Adding a batch of equipment

  1. In a separate temporary dataset, run equipment add name/Batch Test Camera category/Photography condition/GOOD count/3 notes/Shared kit. Expected: three new rows with distinct UUIDs, AVAILABLE status and identical supplied details; feedback lists all three UUIDs and the full equipment directory opens.
  2. Repeat without count/, then with count/1. Each command adds one unit and opens its details.
  3. Try count/0, count/-1, count/101, count/1.5, a blank count/, and count/2 count/3. Expected: an error, no new records, and no save. Correct the input and retry.
  4. Run equipment search q/NoMatchingBatch, then add a valid batch. Expected: the old filter resets and the directory includes the new units. Repeating a batch retains distinct UUIDs and warns about pre-existing matching units, not the new units within the same batch.
  5. Exit and relaunch from the same folder. Expected: all units retain their original UUIDs and details. Use equipment view uuid/UUID with each actual generated UUID to verify independently.

Editing, deleting and restoring equipment

  1. Add two matching units with equipment add name/Maintenance Camera category/Photography condition/GOOD count/2. Record both UUIDs as A and B. Replace these placeholders in all following commands.
  2. Run equipment edit uuid/A name/Updated Camera condition/FAIR notes/Checked then equipment edit uuid/A notes/. Expect A's UUID unchanged, updated details and cleared notes; B remains unchanged. Restart and verify.
  3. Try equipment edit uuid/A, equipment edit uuid/A name/, and a no-change edit. Expect an error and no save.
  4. Assign A to an active test member with valid dates. Edit its condition to DAMAGED: expect ASSIGNED until return, then UNAVAILABLE. Attempt deletion while assigned: expect refusal and no record/history changes.
  5. Return A, then equipment delete uuid/A. Expect a retained [DELETED] row in equipment list, no new loans permitted, and exclusion from active search/inventory totals. equipment search status/deleted should find it. Restart: the flag, UUID, details and closed loan records must remain in the saved data.
  6. Try editing/deleting A again: expect rejection. Run equipment restore uuid/A: expect the same UUID and details, still DAMAGED/UNAVAILABLE. Repeating restore is rejected. Repair with an edit to GOOD and verify that assigning a new loan succeeds. B must remain unchanged throughout.
  7. Check equipment search status/all, direct UUID navigation and query refresh after rename/restore. Automated transaction tests separately inject partial writes/failed atomic moves; do not simulate filesystem failures against a real user dataset.
