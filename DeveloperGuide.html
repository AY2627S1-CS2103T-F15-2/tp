Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

Command routing and legacy compatibility

LogicManager.execute() first calls AddressBookParser.parseCommand(). The root parser accepts member, equipment, and loans, delegating to their family parsers and then the appropriate leaf parser (for example, EquipmentCommandParser and EquipmentAddCommandParser). It also accepts undo, redo, mode, help and exit. Family and leaf parsers remain responsible for validating subcommands and arguments.

The retired top-level words add, edit, delete, clear, find, and list now reach the existing unknown-command branch and throw ParseException("Unknown command."). In particular, list members is rejected; the supported command is member list. Rejection occurs before a command is constructed or executed, before a transaction snapshot is created, and before storage is called.

For supported commands, LogicManager executes transactional mutations on an isolated model snapshot, saves that candidate state, and publishes it to the live root only after saving succeeds. Commands marked isReadOnly() return without saving. This retirement does not change those execution rules.

AddressBook is still the shared root for persons, members, equipment, and loans. Its name and the getAddressBook()/saveAddressBook() APIs do not identify disposable person-only behavior. Existing JSON persons data is retained and round-trips when supported commands save. Person value classes used by members, legacy command/parser implementations and their unit tests, and the legacy UI panel remain for a separate dependency-aware cleanup. Removing public routes does not remove stored records.

Storage component

The supported unversioned schema treats omitted/null members, equipment and loans as empty. Retain both forms for legacy compatibility; saves canonicalize them to [] without touching populated collections. No migration or warning distinguishes null from absence in this schema. Missing member/ equipment deleted flags still mean active; explicit null flags remain invalid. For manual verification, load a legacy persons-only file with each collection omitted, null and empty, save/reload, and compare the retained persons. Use only disposable data.

Directory search and inventory planning

MemberCommandParser and EquipmentCommandParser delegate search arguments to DirectorySearchCommandParser. It validates the allowed prefixes and sort fields, then constructs an immutable DirectoryQuery and a DirectorySearchCommand for the requested directory. Search defaults to active records; status/deleted and status/all expose retained records.

DirectorySearchCommand counts matches using DirectoryQuery, then returns a CommandResult containing DisplayRequest.members(query) or DisplayRequest.equipment(query). Since the command is read-only, LogicManager returns without creating a transaction snapshot or saving data. Equipment queries additionally use Model.getAvailability to derive availability from current state.

MainWindow passes the same query to the directory list and its summary before refreshing them. Both evaluate the query against current data, keeping displayed rows and matching counts consistent. Sorting affects returned snapshots rather than stored records. Navigation requests without a query preserve the current criteria; explicit list commands pass DirectoryQuery.all() to reset them. After mutations, the shell refreshes the views with their retained queries and recovers selection by NUS ID or equipment UUID when possible.

EquipmentDirectorySummary.refresh builds inventory summaries with InventoryGroups.group, passing DirectoryQuery.all().equipment(data, availabilityLookup) as the matching units. It formats each group using EquipmentPresentation.counts(group.units(), availabilityLookup). The activity below shows this GUI path when availability can be resolved; it does not describe the retained summarize helper.

Each group uses a pair of normalized category and name values, keeping the two keys separate even when either contains a display separator. InventoryGroups.group retains all physical units under each key and emits groups in first-match order. For this caller, the all-records query supplies default category/name/UUID order, so groups appear in category/name order. Other callers can pass a filtered or sorted matching list; group.matching() records those matches while group.units() retains the full group. The summary uses the all-records query, so its group counts are independent of search filters.

EquipmentPresentation.counts looks up each active unit's availability by UUID and counts deleted units separately without an availability lookup. It displays zero for absent availability states and adds a deleted count only when nonzero. The summary prefixes these counts with the category and name of the first unit in the group, preserving its stored spelling rather than displaying the normalized key. If its initial scan cannot resolve an active unit's availability, the summary displays Inventory groups unavailable: inconsistent equipment data. instead of group lines. These derived summaries preserve individual equipment identities and do not introduce a stored quantity field.

Equipment editing, deletion and restoration

Each Equipment is an immutable physical unit. EquipmentEditCommand builds a replacement with the stored UUID and any supplied details. AddressBook.setEquipment permits only active-to-active edits; UniqueEquipmentList.setEquipment checks UUID equality and replaces the value at the same index. Name/category changes affect derived inventory groups, never sibling units. Unspecified legacy text is retained verbatim; new text uses equipment-add validation. Notes can be cleared explicitly.

AddressBook.removeEquipment now marks a unit deleted after checking that no open loan exists. restoreEquipment clears the flag. Both retain UUID, details and closed loans. This supersedes the historical scaffold's permanent deletion. Member and equipment restoration have no time limit.

Lifecycle is separate from condition and loan status. Editing condition while loaned is allowed: ASSIGNED remains derived from the open loan; on return the edited condition controls availability. Deleted units derive UNAVAILABLE, cannot receive open loans, and are excluded from active availability counts. Inventory groups retain them and report their deleted count separately. Root loan validation applies this invariant both to new loans and complete dataset replacement/loading.

JsonAdaptedEquipment writes a boolean deleted. An absent flag defaults to false for earlier files; explicit null and non-boolean values fail loading. Closed loans may reference deleted equipment. All maintenance commands are transactional: execute against a snapshot, save atomically, then publish. No-change/rejected edits and failed writes leave live state and previously saved bytes unchanged.

Directory queries share DirectoryQuery.Status across members and equipment. Equipment search defaults to active; status/deleted|all exposes retained units. List resets to all states without recording history. Cards label deleted units; details show lifecycle state and a restore command. Edit/restore navigate to the same UUID, retaining query criteria even if that unit no longer matches. Total counts include deleted units; availability counts include active units only, while groups also report retained deletions. The Loans tab and entity details show the retained completed loan history.

Undo/redo feature

The CLI commands undo and redo restore complete record states within the current session. AddressBookHistory is an immutable value owned by ModelManager, composed with the existing AddressBook rather than replacing or subclassing its observable root. It retains at most ten reversible changes (eleven snapshots). Each snapshot has independent collection containers for members, physical equipment, loans and retained legacy persons; immutable entity values may be shared.

The class diagram below shows only the command, persistence and record-history collaborators. Parser classes, collection wrappers, domain entities and preferences are omitted. The live model and each candidate own separate roots; multiple immutable history values may reference the same private stored snapshots. Accordingly, snapshot sharing uses ordinary associations rather than exclusive composition. The ordered states association has multiplicity 0..11, including empty history before the first change. An AddressBook snapshot has no ModelManager owner, hence 0..1 at the model end of root composition; every model still owns exactly one root. The logic associations allow model/storage collaborators to be shared by more than one LogicManager instance.

The first successful mutation records both the preceding state and the candidate state. Later mutations append a snapshot and a short action description, such as equipment add, without retaining command parameter values in the description. Once ten changes are retained, the oldest change and its preceding snapshot are discarded. A batch creation, issue or return is one history entry regardless of unit count.

Transaction and persistence boundary

  1. AddressBookParser routes bare undo/redo through their no-argument parsers. Both reject extra text and prefixes using LaplaceArgumentParser.
  2. LogicManager creates an isolated candidate through Model.createTransactionSnapshot(). Candidate records and preferences are copied; the immutable history can initially be shared safely.
  3. An ordinary transactional command changes candidate records. Command.recordsHistory() tells LogicManager to call recordAddressBook(previous, description) on that candidate. A real change discards any redo branch; an unchanged candidate leaves history untouched.
  4. UndoCommand/RedoCommand instead check availability and navigate the candidate's existing history. They return DisplayRequest.unchanged() and do not record another action. Redo restores the recorded snapshot directly, preserving UUIDs, loan dates, conditions and references without replaying commands.
  5. The existing atomic JSON save persists the candidate records once. Only after success does Model.publishTransaction() publish the candidate records and history to the live model. It preserves the live observable root and current preferences. Parse, validation and save failures leave live data, history position, redo availability and the previously saved file unchanged.

Record replacement validates all collections before publishing. AddressBook.resetData() installs the new records and runs the model's history-publication action before resuming list notifications. This keeps synchronous observers' record values and undo/redo availability consistent during transaction publication, explicit whole-model replacement, and direct undo/redo navigation. Validation failures leave the previous history intact; replacing identical records can still update history without list events.

The logic sequence traces one undo through parsing, availability checks, candidate execution, atomic saving and publication. AddressBookParser delegates argument validation and command construction to UndoCommandParser. The Storage lifeline abbreviates StorageManager, JSON serialization and AtomicFileWriter. Invalid arguments stop during parsing; unavailable undo stops during execution. Neither reaches saving. A save error discards the staged result without consuming a live history step.

The next two sequences expand only the model operation inside that candidate. They distinguish the candidate's stable root from the defensive copy returned by getCurrentState(). before and restored are separate immutable history values; position changes never mutate a history shared with the live model. Field assignment is shown as a note, rather than as a fictitious method call.

redo follows the same logic/save/publication sequence with RedoCommandParser, RedoCommand, canRedoAddressBook() and redoAddressBook(). Its unavailable error is Nothing to redo..

The model exposes canUndoAddressBook(), canRedoAddressBook(), undoAddressBook() and redoAddressBook(). Direct history navigation requires an available step; commands translate unavailable history into Nothing to undo. or Nothing to redo.. Successful feedback identifies the action: Undid: equipment add. or Redid: equipment add.. The history object guards invalid direct navigation with IllegalStateException and returns defensive copies of stored record states.

Read-only queries, navigation, help, exit and appearance changes do not add history entries or invalidate redo. Their isReadOnly() declarations also bypass domain-record saving. A failed record save does not prevent navigation, Help or normal exit; shutdown preference saving remains separate. A new successful record mutation after undo discards the undone branch. Explicit whole-model replacement with setAddressBook() starts fresh history; transaction publication uses its separate API to retain it.

History is session-only and is not serialized. Restarting loads the most recently saved record state with no undo or redo available. Preferences, search filters, window geometry and command-input history are outside record history. The existing shell refreshes summaries, groups, holdings and loan history; when undo removes a displayed exact record, it returns to the corresponding filtered directory. No undo/redo buttons or new shortcuts are provided.

Retention limit and command flow

After twelve successful record changes, only snapshots s2 through s12 and the ten actions between them remain in the current history. The earliest reachable state is s2: ten undos reach position 0, and ten redos can return to s12. These limits apply to reversible commands, not the number of records. Older history values referenced transiently during a transaction can share stored snapshots; the bound applies to the history retained by each model. A failed save cannot evict entries from the live history.

Only successful transactional saves publish candidate records and history. The nontransactional saving path remains for legacy internal commands that do not declare themselves read-only.

Design considerations and verification

Complete snapshots keep linked member/equipment/loan data consistent and make batch restoration atomic. They cost more memory than per-command inverse operations, so retention is capped at ten changes. Inverse operations would require separate reversal logic for every command and batch failure path.

UndoRedoIntegrationTest verifies identity and loan restoration, lifecycle changes, exact saved states, ten undos/redos, restart behavior and failed-save retries. Shell tests exercise the real command box, preserved filters, missing details, loans and error feedback. ModelManagerTest checks history availability inside synchronous collection listeners, unchanged-record history transitions, and rollback when replacement records are invalid.

Non-Functional Requirements

These are acceptance targets for the intended product, not measurements of the current implementation. Product constraints are adapted from the course project constraints; development-process requirements such as incremental delivery are not product NFRs.

  1. NFR01 — Platform compatibility: The release shall launch and support its documented operations on Windows, Linux, and macOS with Java 25 as the only installed Java version.
  2. NFR02 — Portable distribution: The application shall run from a single downloadable JAR without an installer or separate installation of dependencies other than Java. The JAR shall not exceed 100 MB.
  3. NFR03 — Local operation: Member, equipment, loan, and local backup operations shall work without a network connection, remote server, or external account. Each dataset belongs to one local operator; shared or concurrent access is unsupported.
  4. NFR04 — Editable storage: Persistent records shall use local, human-editable text files without a DBMS. Valid edits made while the application is closed shall load on restart; invalid files shall produce a diagnostic rather than be silently accepted.
  5. NFR05 — Keyboard operation: Every documented record-management operation shall be completable with keyboard input alone. Users shall not need mouse actions to submit commands, inspect results, or correct input.
  6. NFR06 — Display compatibility: At 1920×1080 with 100% or 125% scaling, essential controls and feedback shall not overlap or be clipped. At 1280×720 with 150% scaling, every operation and its result shall remain accessible, using scrolling where necessary.
  7. NFR07 — Capacity and response time: With 1,000 members, 5,000 equipment items, and 10,000 loans on a computer with a four-core CPU, 8 GB RAM, and an SSD, at least 95 of 100 executions of each core add, list, exact lookup, delete, issue, and return operation shall display a result within two seconds of submission. Measure after startup, with valid data and no competing intensive workload; include local saving for mutations. Startup with the same dataset shall complete within ten seconds.
  8. NFR08 — Atomicity and durability: After a successful mutation and normal shutdown, restarting shall recover the same records and loan relationships. Validation or reported save failures shall not leave partially updated member, equipment, or loan data. A failed file replacement shall preserve the last valid saved dataset. The same guarantee applies to batch and undo/redo operations as a whole, and to future import/restore operations.
  9. NFR09 — Consistent feedback: Every rejected command shall identify the first detected problem and provide an accepted format or corrective action. Input errors shall not terminate the application, and the submitted command shall remain available for correction. Success and error messages shall be distinguishable by text, without relying on color alone.
  10. NFR10 — Data confidentiality: Laplace shall not transmit member details or inventory records over the network. Diagnostic logs shall omit member names, phone numbers, email addresses, and raw commands containing those values. Local text data and user-created exports rely on the operating system's file access controls; application-level encryption is not promised.

Overdue loan An open loan whose expected return date is before the computer's local date. This definition does not imply automatic notifications.
Active record A member or equipment record included in normal lists, rather than archived or deleted. Active equipment can still be assigned or unavailable.
Archive A proposed operation that removes an inactive member from the active list while preserving their record and history.
Delete Marking a retained record deleted, allowed only without open loans. Its identity, details and closed history remain stored.
Restore Reactivating a retained deleted member or equipment unit without a time limit, preserving identity and history.
Snapshot A complete local export of Laplace's persistent records and their relationships at a point in time, used as a backup. It differs from importing selected member or equipment records.
Fuzzy search Proposed matching of incomplete or approximate text against records; distinct from the MVP's exact identifier lookup.
Atomic operation An operation whose changes succeed together or leave the preceding consistent state intact.
MVP Minimum viable product; the Week 6 baseline, which is a subset of the full requirements recorded here.
